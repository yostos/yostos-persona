このブログのカバー画像の出力をWebPからAVIFに切り替えました。
切り替えるにあたって、記事内の画像をすべて変換したらどれくらい軽くなるのかを実際に測り、
どの画像をどの形式で持つのかを決め直しています。その過程をまとめます。

## 画像フォーマット AVIFとは

AVIFは、Alliance for Open Media（AOMedia）が策定した静止画フォーマットです。AOMediaは2015年9月1日に発足しました。設立メンバーはAmazon、Cisco、Google、Intel、Microsoft、Mozilla、Netflixの7社で、発足時のプレスリリースには「相互運用可能でオープン」「ロイヤリティフリー」「Web向けに最適化」といった目標が並んでいます。Googleは当時の状況を「web video innovation was too slow and too closed」と表現していました。

その成果が動画コーデックのAV1です。2018年3月28日にビットストリーム仕様が公開され、同年6月25日に検証済みの1.0.0が出ました。

静止画フォーマットには、動画コーデックのイントラフレーム符号化をそのまま流用するという系譜があります。WebPはVP8から、HEICはHEVCから作られました。AV1に同じことをしたのがAVIFです。仕様1.0.0は2019年2月19日に公開され、最新版は2025年10月16日の1.2.0です。

器にはHEIFを使います。HEICと同じISO Base Media File Format系のコンテナで、中身の符号化だけをHEVCからAV1に差し替えた格好です。HEICと決定的に違うのは、特許ライセンスの交渉なしで使える点です。

フォーマットとしての特徴は次のとおりです。

- JPEGやWebPより高い圧縮効率を持つ
- 12bitまでの色深度、HDR、広色域を扱える
- アルファチャンネル、可逆圧縮、アニメーション、プログレッシブデコードに対応する
- 仕様と実装がともにロイヤリティフリーである

ブラウザ側の対応は、Chrome 85、Firefox 93、Safari 16（iOS）およびSafari 16.4（macOS）、Edge 121からです。最後発のEdgeが2024年1月に対応したことで主要ブラウザが出揃い、[Can I use](https://caniuse.com/avif)の集計では対応率が約95%に達しています。個人ブログで使うぶんには、もう待つ理由はありません。

一方で、使う前に知っておいたほうがよい癖もあります。

- エンコードが遅い。`avifenc`の`-s`（speed）は0が最も遅く、10に近づくほど速くなる
- 既定のクロマサブサンプリングは4:2:0で、細い色付きの線や文字が崩れる
- 可逆圧縮ではWebPに大きく負ける
- ブラウザ以外の取得元、たとえばSNSのクローラーは対応状況が読めない
- 小さい画像ではヘッダの分が効いて、かえって大きくなることがある

後半の3つはこのブログの運用にそのまま効いてきました。以降の節で実測値とともに見ていきます。

## AVIF移行の検証

確かめたいことは3つあります。ブログ全体を移行するとどれだけ軽くなるのか、写真をどの品質値で変換すればよいのか、そして図版にもAVIFを使ってよいのかです。このブログの実データで順に測っていきます。

### 検証の前提と対象

一括変換の対象は、記事で使用している画像すべてです。`avifenc -q 60 -y 420 -s 6`で変換し、変換前後の合計バイト数を比べています。対象は678枚でしたが、このうち2枚は変換できていません。95フレームのアニメーションWebPが1枚と、697フレームのアニメーションGIFが1枚です。AVIF自体はアニメーションを表現できますが、`avifenc`が受け付けるのは静止画だけだからです。残る677枚が集計対象になります。

既存のWebPがすでに非可逆圧縮を通ったファイルである点には注意が必要です。今回はそれをPNGに展開してからAVIFに再エンコードしているので、原本から直接AVIFにする場合とは条件が違います。以降の数字は「いま置き換えたらどうなるか」の目安として見てください。

画質はSSIMULACRA2という知覚品質指標で測ります。CloudinaryのJon Sneyers氏が作った指標で、スコア90が「visually lossless」、70が「high quality（アーティファクトは知覚できるが不快ではない）」、50が「medium quality」という目安が示されています。

### ブログ全体でどれだけ削減できるか

| 区分       | 枚数 |  変換前 | AVIF (q=60) | 削減率 |
| :--------- | ---: | ------: | ----------: | -----: |
| 本文画像   |  169 | 38.9 MB |     14.4 MB |  63.0% |
| カバー画像 |  128 | 21.2 MB |     10.6 MB |  49.9% |
| OGP画像    |  380 |  7.9 MB |      5.6 MB |  28.6% |
| 合計       |  677 | 68.0 MB |     30.6 MB |  54.9% |

全体では55%減という結果です。
OGP画像で削減率が低いのは文字中心のシンプルな画像であるためでしょう。

元の形式ごとに分けると次のようになります。

| 元の形式 | 枚数 |  変換前 | AVIF (q=60) | 削減率 |
| :------- | ---: | ------: | ----------: | -----: |
| WebP     |  634 | 41.1 MB |     24.1 MB |  41.4% |
| JPEG     |   36 | 24.4 MB |      6.3 MB |  74.1% |
| PNG      |    7 |  2.5 MB |      0.2 MB |  90.6% |

JPEGとPNGの削減率が高いのは、枚数が少ないうえに1枚あたりが大きいファイルに偏っているためです。すでにWebPになっている634枚での4割減が、実際の移行で期待できる水準に近い数字だと考えています。

一方で、677枚のうち40枚はAVIFのほうが大きくなりました。最大で1.66倍です。内訳は本文画像が32枚、カバー画像が8枚で、本文画像の多くは図版やスクリーンショットでした。写真とそれ以外を同じ設定で扱うのは無理がある、ということがここに出ています。

### 写真をどの品質値で変換するか

このブログのAI生成カバー1枚と写真3枚を使い、品質値を振りながらスコアを測りました。比較対象は移行前まで使っていた`cwebp -q 80`です。写真3枚は保存済みのJPEGを基準画像にしているので、この表が見ているのはAVIFとWebPの再エンコード分だけです。

| 設定        | AI生成カバー | 写真A | 写真B | 写真C |
| :---------- | -----------: | ----: | ----: | ----: |
| AVIF q=54   |         65.4 |  63.4 |  71.4 |  64.8 |
| AVIF q=56   |         67.9 |  67.0 |  73.6 |  66.8 |
| AVIF q=58   |         69.0 |  68.5 |  74.6 |  67.7 |
| AVIF q=60   |         71.5 |  71.5 |  76.2 |  69.5 |
| AVIF q=62   |         72.6 |  72.9 |  76.9 |  70.3 |
| cwebp -q 80 |         74.4 |  77.1 |  72.3 |  69.2 |

q=58以下では4枚とも70を割ります。q=60にすると3枚が70を超え、残る1枚も69.5とほぼ境界です。つまり60は、SSIMULACRA2の「高品質」の目安に乗る最小の設定ということになります。

同じ4枚のファイルサイズは次のとおりです。

| 設定        | AI生成カバー |    写真A |    写真B |    写真C |
| :---------- | -----------: | -------: | -------: | -------: |
| AVIF q=60   |     138.2 KB | 414.5 KB | 107.3 KB | 160.9 KB |
| cwebp -q 80 |     181.3 KB | 618.5 KB | 132.8 KB | 199.0 KB |
| 削減率      |        23.8% |    33.0% |    19.2% |    19.1% |

スコアは`cwebp -q 80`と同程度で、ファイルは2割から3割小さくなりました。見た目を落とさずに軽くするという目的には、これで足ります。

### 図版にAVIFを使えるか

変換して大きくなった40枚の多くは図版やスクリーンショットでした。図版でAVIFがどう振る舞うのかを、2つの角度から測ります。

1つ目はクロマサブサンプリングです。AVIFの既定である4:2:0は色差の解像度を半分に落とすため、細い色付きの線が崩れます。1927×864の構成図で測ると次のようになりました。

| 設定              |   サイズ | SSIMULACRA2 |
| :---------------- | -------: | ----------: |
| AVIF q=60 (4:2:0) |  39.8 KB |        76.4 |
| AVIF q=90 (4:2:0) |  61.5 KB |        77.5 |
| AVIF q=60 (4:4:4) |  40.3 KB |        87.7 |
| cwebp -q 90       | 122.5 KB |        76.2 |
| cwebp -lossless   |  42.1 KB |    劣化なし |

4:2:0のままだと、品質値を90まで上げてもスコアは77台で頭打ちになります。`-y 444`にすれば87.7まで戻りますが、それでも非可逆であることに変わりはありません。そして可逆WebPは42.1 KBで、AVIF q=60の39.8 KBとほとんど変わらないサイズに収まっています。同じ容量で劣化なしにできるのですから、図版で非可逆を選ぶ理由がありません。

2つ目は可逆圧縮どうしの比較です。図版やスクリーンショット6枚を`cwebp -lossless`と`avifenc --lossless`の両方で圧縮しました。

| 画像                       | 内容               | cwebp -lossless | avifenc --lossless |   倍率 |
| :------------------------- | :----------------- | --------------: | -----------------: | -----: |
| flow.png                   | 構成図             |         42.1 KB |           222.0 KB | 5.27倍 |
| covid19-graph1.png         | グラフ             |         10.0 KB |            36.4 KB | 3.64倍 |
| covid19-graph2.png         | グラフ             |         11.0 KB |            48.7 KB | 4.44倍 |
| badge.png                  | バッジ             |         11.4 KB |            25.7 KB | 2.26倍 |
| decibel-spotify-preset.png | スクリーンショット |         15.4 KB |            38.2 KB | 2.48倍 |
| postcard.png               | イラスト           |         23.7 KB |           153.0 KB | 6.46倍 |

このブログの図版で試した範囲では、AVIFの可逆圧縮はWebPの2.3倍から6.5倍になりました。可逆で残したい画像にAVIFを使う意味はありません。

## まとめ：画像形式の使い分け方針

検証の結果、このブログでは画像の性質で2つに分けると決めました。

- 写真やAI生成のイラストは非可逆のAVIFを使用
- 図版やスクリーンショットは可逆のWebPを使用
- 適用するのは新規記事のみ、既存記事のファイルは移行しない

写真とAI生成のカバー画像は次のコマンドで変換します。

```bash
avifenc -q 60 -y 420 -s 6 --ignore-exif --ignore-xmp input.png output.avif
```

`-y 420`はクロマサブサンプリング、`-s 6`はエンコード速度の指定です。`--ignore-exif --ignore-xmp`はExifとXMPのメタデータを出力に含めません。

図版やスクリーンショットは、WebPの可逆圧縮を使います。

```bash
cwebp -lossless -z 9 -exact input.png -o output.webp
```

`-z 9`は可逆プリセットの圧縮レベルを最大にする指定、`-exact`は透明部分のRGB値を保持する指定です。

OGP画像（`social_media_card`）はWebPのまま据え置きます。ブラウザではなくSNSのクローラーが取得する画像なので、対応状況が読めない形式に変えるリスクのほうが、数MBの節約より大きいと判断しました。`npm run ogp`で自動化しているので、出力は現状維持することにしました。

まとめると、このブログの使い分けは次の3つになります。

| 用途                             | 形式           | コマンド                                                               |
| :------------------------------- | :------------- | :--------------------------------------------------------------------- |
| 写真、AI生成のカバー画像         | AVIF（非可逆） | `avifenc -q 60 -y 420 -s 6 --ignore-exif --ignore-xmp in.png out.avif` |
| 図版、グラフ、スクリーンショット | WebP（可逆）   | `cwebp -lossless -z 9 -exact in.png -o out.webp`                       |
| OGP画像                          | WebP           | `npm run ogp`                                                          |

冒頭のカバー画像も、この方針で作った最初のAVIFです。1536×864で41.9 KBに収まりました。
