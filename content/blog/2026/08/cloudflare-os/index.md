2026年8月5日、CloudflareがAIワークスペース「Cloudflare OS」をApache-2.0ライセンスで公開しました。翌日にはHacker Newsのフロントページに載り、[GitHubのリポジトリ](https://github.com/cloudflare/cloudflare-os)のスターは公開初日に3,900、8月19日時点では8,500を超えています。

"OS"という名前を見て、私はまずLinuxやWindowsの系譜を想像しました。しかし発表内容を読むと、これは伝統的な意味でのOSではありません。Cloudflareが自社の全社員向けに作って運用してきた社内AIワークスペースを、丸ごと公開したものです。名前の大きさと中身のあいだにある落差が、この製品を考える上での出発点になります。

## Cloudflare OSとは何か？

Cloudflare OSが何かを語る前に、まず下回りから見ていきましょう。この製品を実装しているのは、既存のCloudflare製品の束ね直しです。Workers、Durable Objects、Access、AI Gateway、R2に、ツール接続のMCPとRPCのCap'n Webが加わります。新しいインフラを作ったわけではありません。

役割で並べ替えると、計算資源、状態の保持、認証、AIモデルへの接続、ストレージ、そしてツール接続という並びになります。これは2026年にエージェント基盤を名乗る製品であればどこも持っている組み合わせで、この層に「OS」と名乗る根拠はありません。インフラとして見る限り、ここにあるのは典型的な**生成AIエージェント基盤**です。

Cloudflareは、生成AIエージェント基盤としての機能を3つに分けて説明しています。

| 構成要素                     | 内容                                                                             |
| ---------------------------- | :------------------------------------------------------------------------------- |
| Agent Workspace              | ブラウザのチャットUI。非エンジニアの利用も想定している                           |
| セキュリティとガバナンスの層 | 外部へはGatekeeper経由でしか届かない。権限はcapabilityで渡し、アクセスは記録する |
| Gadget                       | 成果物1つごとに、エージェントが専用のソフトウェアを書いて動かす                  |

Gadgetは一から作らせるほかに、既存のGadgetのコードを雛形にして作れます。この雛形はBlueprintと呼ばれ、標準では3つが同梱されています。

- workspace-docs: ドキュメント
- workspace-sheets: スプレッドシート
- workspace-slides: スライド

事務作業の最低限だけが置かれていて、あとは各自で増やす、という構えです。自作したGadgetも、中身のデータは渡さずコードだけをBlueprintにして配れます。

ここで各自が増やすものとして想定されているのが、long-tailの業務です。1件あたりの規模は小さいものの種類がとにかく多く、IT部門に頼むほどではないけれど手元では面倒、という類の作業を指します。特定のチームだけが使う集計表、月に数回しか動かさない進捗の一覧、部署内で回している申請の受付といったものです。数が多すぎて基幹システムには載らず、これまでExcelやAccessが引き受けてきた領域でもあります。

まとめると、Cloudflare OSは、利用社員が自らチャットで指示して成果物と個々の成果物専用のGadgetを構築できる生成AIエージェント基盤です。アプリごとに資源を割り当てて互いに隔離し、外部との入出力を仲介するという役回りを見れば、比喩として「OS」は的外れとも言い切れませんが、基本的には各社のエージェント基盤と大きく変わりません。

## ドキュメント単位に閉じるという設計

**ドキュメント単位の隔離**が、設計方針の中でもっとも目を引く部分です。アプリの実体であるGadgetは、ドキュメント1つにつきDurable Objectのインスタンスが1つ割り当てられ、専用のWorkerとSQLiteストレージを持ちます。ブラウザ側ではiframeに閉じ込められ、CSPの`connect-src 'none'`によってネットワークへの到達そのものが断たれます。外に出たければGatekeeperを通すしかなく、そのGatekeeperが認証情報を握ってスコープを絞った操作だけを許す、という構造です。

この作りが効くのは、中身が検証されていないコードを前提にできるからです。Gadgetを書くのはエンジニアではなく、非エンジニアの指示を受けたAIで、レビューやテストは通っていません。不具合があっても、そのGadgetは外部へ接続する手段を持たず、隣のドキュメントのデータにも手が届きません。悪意のある指示が埋め込まれたファイルを読んでしまった場合も同じです。社内システムに届くのは、Gatekeeperを通ったあらかじめ絞られた操作だけです。さらに生成物を他人へ共有する段になると、元になったデータへの権限を相手が持っているかどうかが、あらためて確認されます。Cloudflare自身、非エンジニアが安心して好きに触れることを設計目標として挙げています。

Cloudflare OSを主導したKenton Vardaは公開時に、これは10年前の自分のスタートアップSandstorm.ioのリメイクだと述べています。10年前この構想が広まらなかった理由は2つあります。対応アプリが足りなかったことと、インスタンスごとにコンテナを立てる実行基盤が重すぎたことでした。10年を経て、ミリ秒起動するWorkersが前者の重さを解き、生成AIが「対応アプリを人が移植する」という前提そのものを消しました。エージェントがその場でアプリを書くのであれば、アプリストアを埋める必要はありません。

つまりCloudflare OSの中核にある思想は、生成AIブームの産物ではなく、条件が揃うのを10年待っていた設計です。

## OSSだがCloudflare前提

「OSSで公開」「セルフホスト可能」と聞くと、自社データセンターに閉じた運用を思い浮かべるかもしれません。しかしCloudflare OSのセルフホストとは、Cloudflareのネットワーク上にある自社アカウントへデプロイすることを指します。**実行基盤は必ずCloudflare**です。OSSであることは、中身が透明で、自由に改変でき、UIに縛られないという意味です。インフラからの独立を意味するわけではありません。

これがOSSであるCloudflare OSのマネタイズの源泉だと考えています。Cloudflare自身が明言しているわけではありませんが、razor-and-blades、つまり本体を無料で配りそれが消費する下回りで課金する構図です。課金ポイントは、Workersの実行、Durable Objects、Workers AIとAI Gateway、R2、そしてAccessやZero Trustのシートに分散しています。
OSSは自社クラウドの消費を増やすための入口だという見立てです。ダッシュボードに統合されたマネージド版も予告されています。

この構造は、AWS上に同じものを自作した場合と経済モデルとしては変わりません。自分のアプリを他社クラウドに載せて従量課金される、ロックインの形も同じです。ただし専有リソースをあらかじめ確保する方式とは違い、Cloudflareはサーバーレスのマルチテナントです。もっとも、完全に使った分だけというわけでもありません。Gadgetの実体であるDurable Objectsは、メモリ上で起きているあいだwall-clockで課金され、リクエストが来ていなくても料金が発生します。

## 2026年は「エージェント基盤に名前を付ける」年だった

Cloudflare OSを「生成AIエージェント基盤」とすると、この分野ではCloudflareはむしろ後発です。
ハイパースケーラー3社は数か月から半年先行して、同種の基盤を投入しています。

| 企業       | 基盤の名前                          | 時期                    | 性格                                                          |
| ---------- | ----------------------------------- | ----------------------- | ------------------------------------------------------------- |
| AWS        | Bedrock AgentCore                   | 2025年10月13日 GA       | Runtime、Gateway、Memory、Identity、Observabilityの部品群     |
| Google     | Gemini Enterprise Agent Platform    | 2026年4月22日 Next '26  | Vertex AIの後継。Workspaceと密結合し、サンドボックス実行とA2A |
| Microsoft  | Microsoft IQとFoundry Agent Service | 2026年6月2日 Build 2026 | Work IQなど4層のコンテキスト層。M365エコシステムに密結合      |
| Cloudflare | Cloudflare OS                       | 2026年8月5日 OSS公開    | 社内で運用済みの完成ツールをApache-2.0で配布                  |

各社に共通するのは、エージェント基盤に固有の名前を付けてブランド化したことと、ツール接続の共通土台としてMCPを採用したことです。

Cloudflare OSが他社と違うのは2点です。

1. **非エンジニアによるエージェント利用が前提:** 他社の基盤は、エージェントを組むのがエンジニアであることを暗黙の前提にしている。Cloudflare OSは逆で、レビューやテストを通っていないコードが動く前提に立つ。成果物1つごとに隔離し、ネットワークを最初から断ち、認証情報をコードに渡さないのは、そのためである
2. **企業での提供方法:** 他社が出しているのはIT部門が組み合わせてエージェントを作るための構成要素だが、Cloudflare OSは自社の全社員が数か月使ってきた完成品がそのまま、しかもApache-2.0で出てくる

機能として「AWSでは同じことができない」わけではありません。IAMとAgentCoreのIdentityやGatewayを組み合わせれば、同等のことは実現できます。違うのは、それを誰かが組み上げなくても最初からそうなっている点です。

## これは"OS"ではなく、業務アプリの器である

では、Cloudflare OSで実際に何が作られているのか。ドキュメント、スライド、スプレッドシート、ちょっとした集計、小さな社内アプリ、定型作業のワークフローです。

エンタープライズITで「アプリケーション」と言えば、通常は基幹系を指します。ERP、会計、受発注、在庫、勘定系。トランザクションの整合性が求められ、可用性のSLAがあり、監査に耐える必要があります。壊れれば業務が止まるもの、いわゆるsystems of recordです。Cloudflare OSが生成するものは、そこには届きません。OA用途、systems of engagement、long-tailのシャドーITといった領域です。

つまり本物の業務システムはGatekeeperの向こう側にあり、Cloudflare OS自身はその前段に立つフロントであり糊の層です。"an open platform for agents, apps, and work"という名乗り、とりわけ"OS"と"apps"という語の選び方は、実態より大きく見せています。

もっとも、名前が大げさであることと、カテゴリとして無価値であることは別の話です。ここからが本題になります。

## KintoneとMulmoClaudeと同じ家系

Cloudflare OSを理解するのに一番近い補助線は、他社のエージェント基盤よりもKintoneではないかと思いました。軽量な業務アプリを部品から組む、という核心が一致しています。部品のライブラリがあり、アプリの器があり、そこに近年は生成AIによるアプリ生成が加わる。この構図は両者で同じです。

そして[私が愛用している](@/blog/2026/07/building-contacts-database-mulmoclaude/index.md)MulmoClaudeも非常に近い系統にあると思います。

三者の違いは、生成の主体と、想定するスコープです。

| ツール        | 誰が組むか                       | 中心にあるもの                 |
| ------------- | -------------------------------- | ------------------------------ |
| Kintone       | 人間がノーコードで組む           | チーム、構造化DB、ワークフロー |
| Cloudflare OS | エージェントが実コード込みで生成 | 企業全体、ガバナンス付きの共有 |
| MulmoClaude   | エージェントが対話から生成       | 個人のワークスペース、成果物   |

long-tailやengagementの層に向けたAIアプリ基盤は、どこも同じ形に収束しつつあります。Cloudflare OSが特別なのではなく、ノーコードによる市民開発が生成AIを得たときに行き着く先が、たまたまこの形だったということでしょう。

この見立ては、"OS"という名前への違和感を少し和らげてもくれます。Kintoneは基幹系ではありませんが、正当な業務アプリのカテゴリとして市民権を得ています。

ただし過大評価は禁物です。できるのは軽いlong-tailだけで、複雑な業務ロジックや厳密な整合性が要る場面では手が止まります。生成AIのアプリ生成も同じで、動く小物はすぐ出てきますが、保守、データの一貫性、権限設計、エッジケースの処理には結局人手が要ります。「作れる」と「運用に耐える」のあいだは、思っているより広いままです。

本質は「IT部門に頼むほどでもない雑務を、その場で楽にする」道具であって、革命ではなく時短だと捉えるのが妥当だと思います。

## EUCの亡霊、あるいは誰がこれを維持するのか

そして、この家系のツールには必ず突き当たる問題があります。作った業務アプリを、誰がどう維持するのかという問題です。

かつてエンドユーザーコンピューティング(EUC)が抱えた病理は、よく知られています。

| 病理                   | 内容                                                                                 |
| ---------------------- | :----------------------------------------------------------------------------------- |
| 属人化                 | 作った本人しか仕様を知らない。ドキュメントはなく、異動や退職でブラックボックスになる |
| 野良アプリの増殖       | IT部門が把握しないアプリが社内に散らばり、棚卸しも統制も効かなくなる                 |
| 塩漬けとデータの人質化 | 改修できないまま動かし続け、データが特定のアプリに囲い込まれる                       |

構造的な皮肉は、ノーコードが「作る敷居」を下げても「保守する敷居」は下げないことです。素人が速く大量に、保守できないものを量産できるぶん、事態はむしろ悪化しえます。1990年代から2000年代の「Excelマクロ地獄」「Accessデータベース地獄」が語られたときと、道具が変わっただけで病理は変わっていません。

Kintoneには監査ログや、管理者が1人しかいないアプリを洗い出すガバナンス機能があり、統制の側には手が打たれています。しかし棚卸しができることと、そのアプリを引き継げることは別です。作った人が異動すれば、なぜその形にしたのかは失われます。作る敷居を下げた分だけ、この保守の問題はより広く組織に行き渡ります。
MulmoClaudeはそもそも個人利用を想定しており、使い捨て前提なので、この病理は当てはまりません。

では、Cloudflare OSはこの病理にどのように手を当てているのでしょう。

先に見たドキュメント単位の隔離とGatekeeperは、セキュリティの話であると同時に、EUCの統制のメカニズムでもあります。

Excelマクロが厄介だったのは、そのファイルが誰のPCにあるのか誰も知らず、埋め込まれた接続情報が作者の退職後も生き続け、データそのものがファイルの中に囲い込まれていたからでした。Cloudflare OSでは、アプリはGadgetとして基盤の上に載り、社内システムへの経路はGatekeeperに一本化され、どのアプリがどのデータを見たかは記録に残ります。少なくともIT部門が棚卸しをする手段はある、という点で、ファイルサーバーに散らばったマクロとは事情が違います。

認証情報をアプリに持たせない設計も、ここで効いてきます。作った本人の権限が失効すればアプリの持つcapabilityも一緒に失効するので、退職者の作ったものが基幹システムを叩き続ける事態は起きにくくなります。放置されたGadgetは、危険なまま動き続けるのではなく、単に無力になるわけです。データが元のシステム側に残り、アプリはその上に載る窓でしかない点も、人質化を弱めます。かつてのEUCで実際に事故になったのは、この「勝手に外へ手を伸ばす」部分でした。そこは確かに塞がっています。

手当てが届いているのは、統制と被害半径の側です。残るもう半分、つまり中身を誰が理解しているのかという問題には、この設計は何もしません。そして生成AIが加わると、ここはもう一段悪くなりかねません。Cloudflare OSのように非エンジニアが使うことを前提にした設計では、そもそもコードを読む人がいません。属人化を通り越して無人化です。保守の観点だけを見れば、これは退化とも言えます。

Cloudflare OSがこの点をどう設計しているのでしょうか。
GatekeeperとcapabilityはCloudflare OSが既存の社内システムとどう連携するかをよく統制します。しかし、生まれたアプリを3年後に誰が直すのかは統制してくれません。

答えは設計そのものに書かれています。成果物1つごとに独立したGadgetを与えるということは、共通のコードベースが存在しないということです。Blueprintから作ったGadgetにも、後から元の修正を反映する仕組みはありません。これらを維持する前提は置かれていません。MulmoClaude同様、個人の中で完結し使い捨てるものとして設計されていると考えます。

課題は、組織が使い捨てと理解して使うかどうかだけです。
