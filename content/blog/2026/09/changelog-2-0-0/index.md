Keep a Changelogは2026年6月7日に[Changelog 2.0.0](https://keepachangelog.com/en/2.0.0/)を発表しました。前のバージョンの1.1.0は2019年2月の発表なので、7年ぶりのメジャーアップデートです。まだ日本語サイトが出来ていないようなので、主な変更点をまとめてみました。


## バージョニング方式の変更

1.1.xまでのGuiding Principlesでは「[Semantic Versioning](https://semver.org)に従っているかどうかを書く」とガイドされていました。2.0.0では「どのバージョニング方式を使っているかを書く」というガイドに変更され、[Software versioning(Wikipedia)](https://en.wikipedia.org/wiki/Software_versioning#Schemes)へのリンクが提示されるようになりました。

Semantic Versioningは、一般的な `1.8.1` 、 `1.9.0` のような形式を取り、数字の上げ方に明確な規則を定めています。GNU標準などは、 `major.minor.revision` と似た形式ですが、3要素の意味付けやルールまでは取り決めていません。私自身は馴染みがありませんが、Ubuntuの `26.10` のように「西暦下2桁.月」でバージョン番号を構成する[Calendar Versioning](https://calver.org)という方式もあるようです。

つまり、Semantic Versioningに限らず、Calendar Versioningや単純な番号、日付でもよく、使っている方式を明記すればよいということです。



## 変更タイプの変更

変更タイプ(Type of Change)は `Added`・`Changed`・`Deprecated`・`Removed`・`Fixed`・`Security` の6つで、1.1.0から変わっていません。

`Changed` と `Fixed` 、 `Security` の3つは違いの説明が入り、わかりやすくなりました。特に `Security` については、他の2つとの違いは緊急性と関心を持つユーザーだと説明されています。CVE番号があれば、次のように先頭に記述します。

```markdown
### Security
- CVE-2026-12345: 不正な形式の入力を解析する際に、範囲外読み取りが発生する問題
```

6つ以外のタイプを作りたくなった場合についての説明も追加されました。本当に必要なら追加してもよいものの、まず必要にはならないとしています。変更の重要性はタイプを増やすのではなく、項目の文面で表せばよいという立場です。よく要望されるタイプの扱いは次の表の通りです。

| 要望されるタイプ      | 2.0.0での扱い  | 理由            |
|--------------------- |-------------- |--------------- |
| Performance           | Changedに書く  | 既存機能の変更である |
| Improved              | Changedに書く  | 同上            |
| New                   | Addedに書く    | 新機能は機能追加と同義 |
| Internal/Housekeeping | 原則として書かない | 内部の整理は記載する意味がない |
| Dependencies          | 影響に応じて該当タイプに書く | 依存関係更新の影響は様々 |
| Known Issues          | 該当バージョンに記すか、Issueトラッカーに書く | 変更ではなく発見されるもの。修正したらFixedに書く |



## 破壊的変更(Breaking Changes)

ガイドに「破壊的変更」の節が追加され、破壊的変更の書き方が明確になりました。CHANGELOGのガイドでは、何が「破壊的変更」にあたるか定義されていません。その代わり、コマンドライン・ライブラリAPI・ネットワークプロトコル・ファイル形式・設定スキーマのうち、どのインターフェースを安定させるのかを明記し、何が壊れるかを書くよう求めています。Semantic Versioningならばメジャーリリースに入るものとしています。

このような変更は `Breaking Changes` のような専用セクションにまとめるのではなく、本来の変更タイプ(多くは `Changed` か `Removed` )の中に書き、 `**Breaking:**` というマーカーを付けるようガイドされています。変更タイプの中に置けば、ChangedやRemovedを読む人が確実に目にできるからです。

```markdown
### Changed

- **Breaking:** `parse()` はエラー時に例外を送出せず、結果オブジェクトを返すように変更。
- **Breaking:** `/api/users` のレスポンスを、フラットな構造から `profile` と `settings` に分けた入れ子構造に再構成。一部の従来のフィールド名(`user_email` など)では値を参照不可。
```



## リリースの文章構造

あるバージョンをリリースしCHANGELOGを書く際に、何をどういう構成で書くかはこれまでもガイドされていましたが記述が分散していました。2.0.0では「Structuring a release」というセクションにまとめられました。

新たに加わったのは、見出し直後の要約(任意)と、各バージョンをcompareの差分につなぐ参照リンクの説明です。CHANGELOGのないプロジェクトの始め方や、バージョン番号を持たない継続リリースでの扱いも追記されました。基本的な書き方は1.1.0から変わっていません。次に1つのリリースの典型的な文章構造を示します。

```markdown
<!-- Unreleased を先頭に置く。次のリリースに入る変更をここに集める -->
## [Unreleased]

<!-- バージョン見出し。[バージョン] - YYYY-MM-DD の形式 -->
## [2.0.0] - 2026-09-30

<!-- 要約(任意)。リリースの主題や目立つ変更を1〜2文で書く -->
ユーザー API を整理し、レスポンス構造を刷新したメジャーリリースです。

<!-- 変更タイプ別のセクション。該当するタイプだけ書く -->
### Added

- `getUser(id)` を追加しました。

### Changed

<!-- 互換性に影響する変更には **Breaking:** を付け、何が壊れるかを書く。長い移行手順はリンクにする -->
- **Breaking:** `/api/users` のレスポンスを、`profile` と `settings` に分けた入れ子構造に再構成しました。`user_email` などの従来のフィールド名では値を参照できなくなります。移行手順は[移行ガイド](https://example.com/docs/migration-2.0)を参照してください。

### Deprecated

- `listUsers()` は次のメジャーリリースで削除します。`searchUsers()` を使用してください。

### Removed

- **Breaking:** `fetchUser()` を削除しました。`getUser(id)` を使用してください。

### Fixed

- ページ指定が 0 のとき、空の結果ではなくエラーを返していた問題を修正しました。

### Security

<!-- CVE 番号があれば先頭に置く -->
- CVE-2026-12345: 不正な形式の入力を解析する際に、範囲外読み取りが発生する問題を修正しました。

<!-- 比較リンクの参照定義。ファイル末尾に置く。Unreleased は最新タグと HEAD の比較 -->
[Unreleased]: https://github.com/your/project/compare/v2.0.0...HEAD
[2.0.0]: https://github.com/your/project/compare/v1.4.0...v2.0.0
```



## LLMの活用

LLMの隆盛を受けて、CHANGELOGとLLMの関係について説明されています。

LLMによる解析という観点では、一貫した形で書けばツールと言語モデルの両方が読解でき、機械向けの別形式ではなくCHANGELOGがシステムの変更内容をこれらに伝えるものと位置付けています。

CHANGELOG作成の際のLLM活用という観点では、コーディングエージェントを使うプロジェクトなら、次のような処理をLLMに任せる指示を `AGENTS.md` や `CLAUDE.md` に書いておくようガイドしています。

-   利用者に関わる重要な変更の要約(git logをそのまま貼らない)
-   変更タイプへの分類
-   本文への変更理由の記述
-   Breakingのマーキング
-   読む価値のない変更の削除

ただし、これは下書きであって何を載せるかの判断は人が行うべきとしています。



## その他の変更

「変更履歴には重要な変更だけを選んで載せ、コミットログの寄せ集めにしない」という考え方は1.1.0から変わっていませんが、次の2点が明記されました。

-   何を載せるかは人が判断すること
-   コミットのたびにタイプ分けする必要はなく、読者向けの要約として書けばよいこと

また、CHANGELOGの冒頭の記述も内容の変更はありませんが、1.1.0では例示だけだったものがガイドとして記述されました。具体的には次の部分です。

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
```

1.1.0のFAQにあった「What about GitHub Releases?」は、GitHubに限らない「CHANGELOGとリリースノートは同じか」という問いに組み替えられ、ガイドに明記されました。両者の違いは次の通りです。

|      | CHANGELOG       | リリースノート                 |
|---- |--------------- |------------------------------ |
| 性格 | 継続的な記録    | 1リリースの告知                |
| 範囲 | 全バージョンの重要な変更すべて | そのリリースの主要な変更を選んだもの |
| 書き方 | 誰にでも読めるよう平易に | アップグレード手順や宣伝的な書きぶりを含むことが多い |
| 置き場所 | リポジトリ内の1ファイル | リリース時に公開される(GitHub Releasesなど) |

結論として、CHANGELOGを正本とし、リリースノートはCHANGELOGから作成して二重管理をしないようガイドしています。リリース時にはCHANGELOGの該当バージョンの節がそのまま下書きになるので、それをコピーし、必要に応じて肉付けすればよいとしています。

GitHub Releasesなどのホスト機能でリリースノートを自動生成できますが、それはホストのデータベースに保存され、リポジトリと一緒には移動しません。ホストを移れば失われるため、下書きとして使うのはよいものの、正本はCHANGELOGにすべきというのがガイドの立場です。



## まとめ

2.0.0はメジャーアップデートですが、既存の書き方を壊す変更はありません。6つの変更タイプ、 `YYYY-MM-DD` 形式の日付、 `Unreleased` や `[YANKED]` の書き方はそのままで、既存のCHANGELOGは引き続き有効です。変わったのは主にガイドで、書式の面では `**Breaking:**` マーカーや任意の要約などが加わりました。

主な変更点を振り返ると次の通りです。

-   バージョニング方式はSemantic Versioningに限らず、使っている方式を明記すればよい
-   変更タイプは6つのまま。Changed/Fixed/Securityの使い分けと、6つ以外を要望された場合の扱いが明確になった
-   破壊的変更は専用セクションを作らず、本来の変更タイプの中に `**Breaking:**` を付けて書く
-   リリースの書き方が「Structuring a release」にまとまり、任意の要約が加わった
-   LLMは下書きに使ってよいが、何を載せるかは人が判断する
-   CHANGELOGを正本とし、リリースノートはそこから作る

全体として、1.1.0から続く「CHANGELOGは人間のためのもの」という原則を、LLMや自動化が普及した今の状況に合わせて示し直したアップデートと言えそうです。1.1.0に沿って書いてきたプロジェクトなら、冒頭のKeep a Changelogへのリンクを2.0.0に更新し、破壊的変更に `**Breaking:**` を付けるところから始めるとよいでしょう。
