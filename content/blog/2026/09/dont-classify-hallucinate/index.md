Doug Turnbull氏の"[Don't classify. Hallucinate!](https://softwaredoug.com/blog/2026/08/10/hypothetical-classifications)"という記事を読んで、
同じようにClaude Codeによるブログ記事のタグ提案を改善できないかと検討してみました。

## "Don't classify. Hallucinate!"の主旨

<!-- textlint-enable ja-technical-writing/no-exclamation-question-mark -->

この記事の主旨は、LLMに物事を特定のTaxonomyに分類させる際、
事前に用意した大量の選択肢をLLMに渡して直接選ばせるのではなく、
あえてLLMにカテゴリ名を自由に生成（ハルシネーション）させます。
それを埋め込み（Embedding）の類似度計算で正規カテゴリにマッピングする手法の提案です。

従来の「500個ある選択肢の中から選べ」という方式では、
選択肢の一覧を毎回プロンプトやスキーマに載せてモデルへ送る必要があり、
その分だけトークンを消費します。

この記事の方式では、次の2ステップを取ります。

ステップ1（LLMに生成させる）
: 正規のカテゴリ一覧を渡さず、「このクエリに合いそうな分類名を自由に考えて作って」とLLMに頼む（例：「茶色のコーヒーテーブル」に対して、LLMが独自に `Furniture` `Living Room` `Tables` `Coffee` と回答）

ステップ2（ベクトルの類似度で変換する）
: LLMが適当に作った分類名の埋め込み（Embedding）ベクトルと、あらかじめ計算しておいた「本物の正規カテゴリ一覧」のベクトルとの類似度（内積など）を計算し、最も近い正規カテゴリに割り当てる。

メリットは、次の2点でしょう。

- 低コスト・高速。毎回大量のカテゴリリストをプロンプトやスキーマに含めて送信する必要がない
- 安価な小型モデルの活用。高度で高価なモデルを使わずとも、軽量な小型LLMでも十分に機能する

## これまでのタグ提案ロジック

これまでは、このブログでは次のようなロジックでClaude Codeにタグを提案させていました。

- 予めタグセットを作成し、各タグを持つ記事全てのベクター値を算出し正規化した値をそのタグのベクター値として保管する
- 提案時は記事内容からベクター値を算出し、タグセットのベクター値と最も近いタグを提案する

このタグごとのベクター値は、そのタグが付いた記事すべての重心にあたります。「このブログで `Cloud` と呼んでいるのは、だいたいこういう内容の記事だ」という実績の平均です。

素直な作りですが、2つの制約がありました。

- タグを1つ足すだけで、タグセット全体のベクター値を計算し直す必要がある
  - 重心は記事から作るため、タグセットを編集するたびに全388記事を埋め込み直すことになる。1回あたり542Kトークン、7秒かかる
- 記事が0件のタグを推薦できない
  - 平均を取る相手がないので、ベクター値は空になる。そのタグが付くまで推薦されず、推薦されないから記事も付かない、という循環に陥る

## タグ提案の新ロジック

Doug Turnbull氏の記事をヒントに以下のように変更しました。

- タグセットのベクター値の算出で全記事をインプットにすることは廃し、タグ名だけのベクター値を算出し保存する
- 提案時は記事内容からClaude Codeに自由に5つの単語を発想させ、連結したものでベクター値を算出する
- 算出したベクター値ともっとも近似のタグを提案する

5語にしたのは、1語よりも記事の内容を的確に言い表せるためです。
5語はスペースで連結し、1本のベクターとして扱います。

タグセットは `data/tagset.toml` で定義しています。
第1層と第2層、そして第2層がどの第1層に属するかを手で書きます。

```toml,name=data/tagset.toml
[[layer1]]
name = "Tech"
description = "ソフトウェア、クラウド、AI、開発ツールなど技術全般。"

[[layer2]]
name = "Cloud"
parent = "Tech"
description = "クラウドコンピューティング全般。インフラとマネージドサービス。"
```

ベクター値は `data/tag-vectors.json` に書き出します。
こちらはスクリプトが生成するので、手では編集しません。

```json,name=data/tag-vectors.json
{
  "schema_version": 2,
  "model": "voyage-4",
  "dim": 1024,
  "input_type": "document",
  "vector_source": "tag_name",
  "normalized": true,
  "updated": "2026-08-31",
  "tags": {
    "Cloud": {
      "article_count": 18,
      "vector": [0.0185, -0.0438, -0.0912, 0.0109]
    }
  }
}
```

`vector` は実際には1024個の要素を持つ配列です。上記は抜粋のため省略しています。
`article_count` は記事数を数えているだけで、ベクター値には使いません。
旧ロジックではこの記事群からベクター値を作っていましたが、
新ロジックでは `name` の `Cloud` という文字列だけを埋め込んでいます。

Claude自体はベクターの埋め込みに対応していないので、Voyage APIを使用しています。
Anthropicの公式ドキュメントにも
"Anthropic does not offer its own embedding model" と明記されており、
そこから案内されている事業者がVoyage AIです。

選定にあたっては、OpenAIとGoogleも含めて比較しました。
決め手になったのはコストです。
`voyage-4` の単価は1Mトークンあたり0.06ドルで、最安ではありません。
OpenAIの `text-embedding-3-small` は0.02ドルですから、単価だけ見れば3倍です。
それでもVoyageを選んだのは、全アカウントに200Mトークンの無料枠が付くためです。
個人ブログの規模では、この枠を使い切ることはまずありません。
単価差が実質的に効かないので、無料枠のある事業者が有利になります。

もう1つは、1024次元で精度が出ることです。
ベクターの一覧はリポジトリに置くため、次元数がそのままファイルサイズになります。

候補のモデルをこのブログの全記事で実際に動かして比較しました。
OpenAIの `text-embedding-3-large` は3072次元でなければ最高精度に届かず、
1024次元に落とすと精度が下がります。
ファイルを3倍に膨らませるか精度を落とすかの二択になるわけです。
Voyageは1024次元のままその水準を保つので、この二択を迫られずに済みます。

以上から、モデルは `voyage-4`、出力次元は1024としました。

## なぜタグ名だけで照合できるのか？

上記のロジックでは記事内容自体は全くベクター化に含まれていません。
なぜ、`Cloud` や `Security` といった数語の文字列に、
記事の内容と突き合わせられるだけの情報があるのでしょうか。

成立するのは、埋め込みモデルがモデル提供者による事前学習で一般的な言語知識を持っているからです。
モデルはWikipediaや書籍、Web上の膨大なテキストを読み込んで、
「どの語がどの語と、どういう文脈で一緒に使われやすいか」を学習しています。
その結果、モデルの内部には意味の近い語が近い座標に並ぶベクトル空間が予めできあがっています。
巨大な連想類語辞典を、モデル自身があらかじめ持っているようなものです。

たとえば `Cloud` という文字列を渡すだけで、モデルは
「空に浮かぶ雲」だけでなく「ITのクラウドインフラ」という意味合いを含む座標を返します。
記事から発想した `infrastructure` や `serverless` といった語も、同じ空間の近い位置に来ます。
このブログで `Cloud` タグが過去どう使われてきたかをモデルが知らなくても、
世間一般でそれらが近い概念であるという知識だけで照合できます。

裏を返せば、モデルが知っているのは世間一般の語義です。
旧ロジックのベクター値は、そのタグが付いた記事の重心でした。
「このブログで `Cloud` と呼んでいるのはこういう記事だ」という実績です。
タグの意味の拠り所を、このブログでの使われ方から世間一般の語義へ移したことになります。

旧ロジックでは、タグの使い方と一般的な語義が食い違ったまま補正されません。
新ロジックでは、タグが世間一般で指す意味に沿って提案されます。従って、タグから想定される記事の内容が読者と噛み合わないということが防げます。

## 新ロジックの精度検証

3つの期間の記事で実測しました。精度は既存のタグと一致している率です。

| 期間                 | 記事数 | 提案が1位 | 上位3位以内 |
| -------------------- | -----: | --------: | ----------: |
| 2026年3〜5月         |     73 |     71.2% |       89.0% |
| 2026年4〜6月         |     61 |     75.4% |       93.4% |
| 直近（5月末〜8月末） |     50 |     76.0% |       88.0% |

既存タグは上記で説明したとおり独自にセットしていたので、読者から見て必ずしも適切であったとは限りません。
ただ、新ロジックでも7割以上は既存と同じタグが提案されます。タグ付けの振るまいは大きく変わらず、精度としては合格点としました。

この精度を保ったまま、旧ロジックの2つの制約が外れました。

- タグセットのベクター値を計算し直すコストが消えた
  - 記事を読まずタグ名だけを埋め込むため、36タグを配列で1リクエストに投入できる。16トークン、1秒未満で終わる。旧ロジックは388記事を9リクエストに分けて542Kトークン・7秒かかっていた
- 記事が0件のタグを推薦できるようになった
  - タグ名さえあればベクター値を持てるため、新しく作ったタグをその日から推薦候補にできる

## まとめ

「分類させるな、幻覚させろ」というタイトルには驚きました。
しかし中身は、仮想の回答文書（Hypothetical Document）を生成してベクトル検索するHyDE（Hypothetical Document Embeddings）を、分類タスクに応用したものです。
分類タスクで問題になるのは、雑多な対象の表現（今回は「記事」）とTaxonomy（今回はタグ一覧）の構造的なギャップです。記事本文とタグ名を直接ベクトル比較しても、きれいには重なりません。

以前はこのギャップをTaxonomy側で埋めていました。コストをかけてタグごとに記事をベクター化し、Taxonomyを記事の表現に寄せていたわけです。今回のアイデアは逆転の発想で、対象のほうをTaxonomyに合わせます。

新ロジックに変更してタグセットの維持が格段にやりやすくなりました。
また独自のタグ付けをしていた部分は、少し読者側に寄り添えたかと思います。

タグ体系は注意深く練り直す必要がありました。

- 独自の使い分けは排除する。`Movie`（自身で制作した動画）と `Films`（観賞した映画）を使い分けていたが、一般には同義である
- `Insight`（洞察）のような抽象的な概念は避ける。タグ付けが安定しない

このロジックはタグ自動アサインではなく、あくまでタグ提案として扱っています。
そのまま使うか書き換えるかは、これまでどおり筆者の裁量で決めます。

原記事は小型で安価なモデルが使えるという利点も挙げていましたが、
今回はそこまで手を付けていません。
このスキルはメインセッションで動くため、そのセッションのモデルがそのまま使われます。
キーワードを選ぶ工程だけをサブエージェントに切り出し、
そのモデルをHaikuに指定すれば、この利点も取り込めるはずです。
